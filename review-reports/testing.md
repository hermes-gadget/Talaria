# Talaria v0.8.2 — read-only test-coverage review

Reviewed 2026-08-03 from `the review worktree`. This is a static QA review: no Git command, Gradle task, unit test, lint task, or connected test was run. The stated green result is therefore the supplied baseline; a static count confirms 214 `@Test` methods across all 62 Kotlin files under `app/src/test`, plus eight JSON fixtures. The review mapped those tests against the 172 Kotlin production files and relevant manifests/resources under `app/src/main`; it also inspected the single instrumentation test under `app/src/androidTest` and the only GitHub Actions workflow. There is no coverage report, so assessments below are behavioral rather than line/branch percentages.

Overall, the suite is broad in feature vocabulary but shallow at Android and orchestration boundaries. It is strongest where logic was extracted into pure functions or a ViewModel accepts lambdas/fakes. It is weakest where production code reaches through `TalariaApp.instance.container`, constructs Android/network collaborators internally, or keeps important behavior private; those seams explain the lack of worker, car, repository, poller, notification-service, and high-value ViewModel coverage.

## Gaps

1. **Car is a zero-coverage feature.** `CarSessionsRepository` combines active-session filtering, up-to-six-way message fan-out, fixed-scope auth, EventClient startup, and PTY delivery, yet none is tested. `SessionListScreen` has meaningful executor/main-thread/destroyed-state behavior and callbacks for reply, retry, quick start, and create-agent. `TalariaCarService` also returns `ALLOW_ALL_HOSTS_VALIDATOR`; whatever the intended trust policy is, a test should lock it down.
2. **The actual reliable-delivery boundary is missing.** `PtyDeliveryBehaviorTest` proves websocket frame shape, but `PtyPromptDelivery` decides whether retrying is safe. Its acknowledgement sources, timeout distinction before/after `frameAccepted`, duplicate/late events, and cleanup are more important than the already-covered frame split.
3. **Workers are only input-tested.** `HermesSyncWorker`'s disabled/no-profile success, retry/failure threshold, foreground-scope guard, fingerprinting, notification dispatch, and widget cache writes are untested. `PairingApproveWorker`'s 408/429/5xx retry policy and `ReplyWorker`'s accepted-frame no-retry rule are untested. `SyncScheduler` interval clamping/unique work and `BootReceiver` action filtering are also uncovered.
4. **Network safety lacks direct regression tests.** `CleartextPolicy` needs a table of HTTPS, opt-in, loopback/private IPv4 boundaries, invalid octets, IPv6, and spoof-like hostnames. `ConnectionSnapshot.sameTransportAs`, secret-redacting `toString`, and `HermesClientFactory` invalidation need coverage. A merged-manifest/instrumentation assertion should verify that HTTP is usable only because the runtime interceptor rejects disallowed targets; XML alone currently permits cleartext globally.
5. **Repositories are effectively untested as repositories.** Retrofit interface tests and `ResponseCache` tests do not establish `HermesRepository` behavior. There is no coverage for cache key scope, invalidation after mutations, HTTP/serialization errors, cancellation, concurrent calls, profile headers, or switching immutable snapshots.
6. **Recent auto-open sync is not executed.** `SessionAutoOpenOwnershipBehaviorTest` duplicates two externally visible rules but cannot invoke the private synchronizer or singleton owner map. The production 30-second delay and wall clock are not injectable, so virtual-time race testing is blocked by design.
7. **Recent car create-agent is not executed.** The create-agent item callback, repository `createSession`, PTY delivery acknowledgement, success/error UI refresh, and duplicate taps have no tests.
8. **Recent voice fallback is only helper-covered.** There is no `VoiceViewModel` test for capability discovery failure/404, the resulting unavailable/partial state, permission denial, manual on-device partial/final/error events, stop/cancel, history bounds, or cleanup. Recorder MP4-to-3GP fallback and audio player generation cancellation are also uncovered.
9. **Compose has zero behavioral coverage.** Critical screens—including Chat, Connect, Voice, notification settings, car-adjacent flows, and management screens—lack semantics and navigation tests. Pure helper tests cannot detect disconnected buttons, wrong routes, missing content descriptions, restoration bugs, or adaptive-layout regressions.
10. **Widgets, tile, and navigation integration are thin.** There is no `TalariaStatusWidget`/tile refresh test, no stale-cache/offline/pending badge test, no widget update trigger test, and no end-to-end deep-link routing test. The parser test does not cover every manifest host or NavRoot's special voice handling.
11. **Notification orchestration is absent from the local suite.** Policy is covered, but service restoration/scope loss, WorkManager action payloads, notifier grouping/dedup/quiet-hours behavior, and completion cancellation are not. The one device test is isolated from CI.
12. **No quantitative coverage or mutation signal exists.** The 214-test count shows breadth, not how much production code is executed. There is no JaCoCo/Kover report, threshold, changed-lines gate, or mutation testing for the many reducers/policies.

## Flakiness-risks

- **Artifact recursion regression is not pinned.** Production now bounds recursively stringified JSON at depth 16, which addresses the reported `StackOverflowError`, but `ArtifactExtractionTest` has no depth-16/depth-17 or self-similar stringified-payload regression. Object/array traversal in `collectJsonCandidates` remains recursive without an explicit structural-depth/element budget, so adversarial deeply nested valid JSON can still consume stack/CPU. Markdown parsing/rendering and the test helper `SimpleMarkdownTest.inlineText` also recursively traverse nested structures without a depth guard; current fixtures are shallow and stable, but fuzzed/untrusted depth is a robustness risk.
- **MockWebServer hangs/timeouts are asymmetric.** `HermesApiContractTest` calls blocking `takeRequest()` without a timeout, so a regression before request emission can hang until the outer test runner kills it. `PtyDeliveryBehaviorTest` is bounded but uses real localhost sockets, `Dispatchers.Default`, and several five-second wall-clock waits; slow or heavily loaded CI can produce false negatives. Its explicit websocket close handshake is a good mitigation.
- **Shared process state can leak.** Robolectric tests use shared preference names, and network tests touch the process-wide `ProfileRegistry`. They clear/reset before and after, which is good, but parallel forks or an early-aborting test could cause order dependence. Production singleton access also prevents safe parallel integration tests.
- **Coroutine scheduling is sometimes too forgiving.** `MainDispatcherRule` uses `UnconfinedTestDispatcher`; this keeps tests fast but can make launched work appear synchronous and hide ordering/cancellation bugs that a queued `StandardTestDispatcher` would reveal. Pollers, callbacks, websocket races, and stale refreshes need explicit virtual-time scheduling.
- **Filesystem/environment dependence is modest but real.** `VoiceAudioDataUrlTest` uses the global `java.io.tmpdir`, real files, and a sparse file just over the maximum size; permission, disk, and cleanup behavior can vary. `SystemViewModelTest` uses a relative shared `build/test-system-cache` path. Prefer per-test temporary folders and assert deletion.
- **Randomness is unnecessary in one assertion.** `NativeOidcPkceTest` asserts two randomly generated values differ. Collision is astronomically unlikely, but deterministic length/alphabet/round-trip assertions or an injectable entropy source would eliminate nondeterminism and enable failure testing.
- **Mocks/fakes versus integration is imbalanced.** Most tests are fast pure units or fake-lambda ViewModel tests, which is a strength. Integration is limited mainly to selected Retrofit contracts and one PTY websocket behavior test; there is no repository-to-HTTP, WorkManager, service/receiver, Compose, car-host, widget, or navigation integration layer to catch wiring failures.
- **Good anti-flake practices already present.** Learning layout uses a seed, quiet-hours tests inject time, cache tests inject a clock, attachment reads are bounded, most coroutine tests drain work deliberately, and external internet is not used. Preserve these patterns when adding orchestration tests.

## CI-status

The repository has one workflow: `.github/workflows/apk-release.yml` (`Build APK`). It runs only for version tags matching `v*` and manual dispatch; it is not a pull-request or ordinary branch-push quality gate.

Current job order:

1. Checkout, Java 17, Android SDK/platform setup.
2. Resolve version and decode the required signing keystore.
3. Run `./gradlew :app:testDebugUnitTest --no-daemon`.
4. Run `./gradlew :app:assembleRelease --no-daemon` with version/signing inputs, then verify/upload the APK and attach tag builds to a prerelease.

Consequences:

- **Unit tests:** yes, all local debug unit tests are invoked in the release job. The reported 214 green tests match the static `@Test` inventory, but this review did not rerun them.
- **Lint/static analysis:** no `lint`, Detekt, Ktlint, dependency analysis, or Android Lint task is present.
- **Connected/instrumentation tests:** no emulator is started and no `connectedDebugAndroidTest`/managed-device task runs. `AgentNotificationsInstrumentedTest` and any future Compose instrumentation tests are dormant in CI.
- **Compose UI tests:** dependencies exist under `androidTestImplementation`, but there are currently no Compose test files and no task runs them.
- **Coverage:** no JaCoCo/Kover task, artifact, or threshold exists.
- **Release compilation:** `assembleRelease` does provide compilation, R8/minification, resource shrinking, manifest merge, and packaging signal, but not device behavior.
- **Gate timing:** keystore decoding occurs before unit tests, so missing release secrets can prevent even the test step. Separating unsigned PR validation from signed tag publishing would make test signal broadly available.

## Recommended-next-tests (prioritized)

### P0 — delivery, scope, and recent-feature correctness

1. **`PtyPromptDeliveryTest` with fake PTY/event clients and virtual time.** Cover acknowledgement by sidecar start/delta/interim/complete and by post-send PTY prompt/agent markers; ignore pre-send/stale events; timeout before frame acceptance permits retry; timeout after acceptance forbids retry; send rejection, event auth failure, close/cancel, duplicate acknowledgements, and exactly-once frame transmission. Reuse this contract from worker and car tests.
2. **`ChatViewModelAutoOpenTest` after extracting/injecting a session synchronizer, owner registry, clock, and poll delay.** Cover baseline versus newly created sessions, pending local creation reconciliation, exactly-one claim across two ViewModels, profile-qualified identities, foreground-profile-only behavior, automation/ended/open exclusions, tab creation/close, ownership release, poll cancellation, and pending timeout. This directly tests recent auto-open sync instead of its current projection.
3. **`CleartextPolicyTest` and `ConnectionSnapshotTest`.** Table-test HTTPS regardless of flag; HTTP denied without opt-in; allowed localhost/`127/8`/`10/8`/`172.16/12`/`192.168/16`/link-local/emulator hosts; boundary and invalid IPv4 values; IPv6 loopback; mixed case/trailing dots if supported; and spoof-like suffixes. Assert `sameTransportAs` field sensitivity, secret-insensitive transport comparison, `toString` redaction, and snapshot changes invalidating clients. Add one instrumentation/merged-manifest check proving the cleartext interceptor gates every REST/websocket client path.
4. **WorkManager tests for `ReplyWorker`, `PairingApproveWorker`, and `HermesSyncWorker`.** Use `TestListenableWorkerBuilder` plus injectable container/repository/delivery seams. Assert fixed connection/profile scope, missing input, success, 408/429/5xx retry, permanent 4xx failure, auth failure, cancellation, and accepted-frame no-retry. For sync, cover disabled/no snapshot, fingerprint changes, first-failure retry versus terminal failure, scope changes mid-run, notifications, activity log, and widget cache updates.

### P1 — car, voice, repositories, notifications

5. **Car repository and screen tests.** Give `CarSessionsRepository` injectable APIs/auth/event/delivery dependencies, then test active-session exclusions, last-five message mapping, six-way concurrency cap, partial failures, 10/20-second timeouts, fixed-scope rejection, `sendText`, and recent `createSession` delivery. With the AndroidX Car test controller, test `SessionListScreen` loading/error/retry/conversation/quick-start/create-agent templates, callback routing, duplicate taps, main-executor publication, destroyed-screen suppression, and rejected executor tasks. Add `TalariaCarServiceTest` to lock down session creation and the intended host-validation policy.
6. **`VoiceViewModelTest` with injectable recorder/player/clock as well as fake API and `SpeechCoordinator`.** Cover OpenAPI success/failure, STT-only/TTS-only/neither, server STT success/blank/error/404, 404 capability removal, manual fallback availability and permission denial, partial/final/error/end, stop/cancel, history ordering/max six, TTS playback completion/error/stop, and `onCleared` cleanup. Add Robolectric tests for `SpeechCoordinator` transient retry cap/offline opt-in extras and recorder MP4-to-3GP fallback/limit callbacks.
7. **`HermesRepositoryIntegrationTest` over MockWebServer.** Exercise real serialization and repository mapping for representative reads/mutations, scoped cache keys, TTL, mutation invalidation, pagination, 204/empty bodies, malformed JSON, HTTP error mapping, cancellation, concurrent refresh/coalescing expectations, profile headers, and active-snapshot switches. Add focused `ChatRepository`/`ConnectionRepository` tests where their policies differ.
8. **Notification Android integration tests.** Robolectric-test `NotificationActionReceiver` WorkManager requests for reply/pair approval/dismiss, including exact connection/profile payloads and blank-input rejection. Service-test `AgentTaskNotificationService` restore/update/stop, completion, terminal transport errors, foreground deadline behavior, and scope loss. Test `TalariaNotifier` permission/quiet hours/grouping/deep links and run the existing real NotificationManager test on an emulator.

### P2 — UI, navigation, widgets, and CI breadth

9. **Compose UI smoke/behavior suite.** Start with `ChatScreen`, `ConnectScreen`, and `VoiceScreen`: loading/error/empty/content states, send/stop/retry actions, permission prompts, fallback visibility, semantics/content descriptions, state restoration, and compact/expanded layouts. Add one happy-path test per management surface whose ViewModel already has unit coverage.
10. **Navigation/deep-link tests.** Test every manifest host (`chat`, `session`, `pairing`, `connect`, `status`, `activity`, `manage`) plus encoded/invalid query and path inputs, cold/warm launch, back stack, and NavRoot's explicit `talaria://voice` routing. Assert widget intents use the explicit `MainActivity` component and cannot be intercepted.
11. **Widget/tile tests.** Cover `TalariaStatusWidget` live success, stale-cache fallback, offline/error, pending pairing/cron badges, refresh/update triggers, and truncation; cover `TalariaTileService` label/state and click intent under connected/disconnected responses.
12. **Scheduling/boot tests.** Assert `SyncScheduler` cancels when disabled, clamps 15–360 minutes, requires connected network, and replaces the correct unique periodic work. Assert `BootReceiver` schedules only for the intended boot action.
13. **CI split and quality gates.** Add a PR/branch validation workflow that needs no signing secret and runs `:app:testDebugUnitTest`, Android Lint, and a coverage report/changed-lines threshold. Keep signed release publishing on tags. Add a managed-device or emulator shard for Compose, WorkManager/service, notification, manifest/network-security, widget, and car smoke tests—at least API 29 and the current target API—using timeouts and uploaded reports.

The highest return comes from making singleton/private orchestration injectable, then testing reliable PTY delivery, auto-open ownership, cleartext/snapshot safety, and worker retry semantics. Those four areas combine recent behavior, data-loss/duplicate-send risk, and security boundaries that the current 214 tests do not reach.
